# AGENTS.md

## Utilix — Repository Guidelines

## 1. Project Overview

Utilix is a lightweight, static website that provides practical browser-based tools for calculations, conversions, text processing, and developer utilities.

The project is built with Astro and TypeScript. Its primary purpose is to make everyday tasks easier through simple, reliable, accessible, and privacy-friendly tools.

### Core principles

- **Simplicity:** Prefer straightforward solutions over unnecessary abstractions.
- **Reliability:** Tool results must be correct, predictable, and tested.
- **Privacy:** Process user data locally in the browser whenever possible.
- **Accessibility:** Interfaces should be understandable and usable by a broad audience.
- **Performance:** Keep pages lightweight and avoid unnecessary dependencies.
- **Maintainability:** Keep responsibilities separated and code easy to understand.
- **Consistency:** Follow established project conventions instead of introducing competing patterns.

### Current product scope

Utilix is a static MVP.

- No database.
- No user accounts or authentication.
- No server-side storage of user input.
- No administrative panel.
- No unnecessary backend infrastructure.

Do not introduce these capabilities unless explicitly requested.

## 2. AI Agent Responsibilities

AI agents working in this repository must act as careful contributors, not autonomous project owners.

### General rules

1. Inspect the relevant existing code before proposing or making changes.
2. Understand how the affected feature interacts with the rest of the application.
3. Reuse existing components, utilities, and conventions where appropriate.
4. Prefer the smallest solution that fully solves the problem.
5. Avoid unrelated refactoring.
6. Do not duplicate existing functionality.
7. Do not introduce dependencies without a clear reason.
8. Do not silently change existing behavior.
9. Explain important architectural or technical decisions.
10. Verify changes with appropriate checks and tests.

### Working with uncertainty

- Do not invent project requirements, API behavior, dependencies, or configuration.
- If an important requirement is unclear, ask before making a potentially consequential decision.
- If several solutions are possible, explain the trade-offs and recommend the simplest appropriate option.
- Clearly distinguish verified facts from assumptions.
- Do not claim that a command, test, build, deployment, or Git operation succeeded unless its result has been verified.

### Scope control

When implementing a task:

- Change only files necessary for the requested result.
- Do not reformat entire files without a reason.
- Do not rewrite working code just because another implementation is possible.
- Do not perform opportunistic cleanup unrelated to the task.
- Report any additional problems discovered separately.

## 6. Architecture and Code Organization

### General architecture

Keep the application divided into clear responsibilities:

1. Astro pages compose the website.
2. Components provide reusable interface elements.
3. Layouts provide shared page structure.
4. The tool catalog describes available tools.
5. Individual TypeScript modules implement tool behavior.
6. Tests verify business logic and edge cases.

Avoid mixing all application logic into Astro page files.

### Tool architecture

Each tool should have its own isolated module whenever practical.

Tool modules should:

- Contain the actual processing logic.
- Avoid direct dependencies on the page layout.
- Prefer pure functions.
- Accept explicit input parameters.
- Return predictable results.
- Handle invalid input clearly.
- Avoid modifying unrelated application state.
- Be easy to test independently.

Keep DOM interaction and presentation separate from processing logic whenever practical.

### Shared functionality

If several tools need the same behavior:

- Look for an existing shared implementation first.
- Extract shared logic only when there is a genuine reuse case.
- Avoid premature abstraction.
- Keep shared utilities focused and independently testable.

Do not create generic frameworks for one-time operations.

## 8. TypeScript and Coding Style

Follow the existing TypeScript strict configuration.

### General conventions

- Use two spaces for indentation.
- Use semicolons.
- Prefer double quotes in TypeScript strings and imports.
- Use descriptive camelCase identifiers.
- Use PascalCase for Astro component filenames.
- Use kebab-case for tool module filenames and URL slugs.
- Use descriptive names for functions, variables, and types.
- Prefer explicit types where they improve clarity.
- Avoid `any` unless there is a justified reason.
- Avoid unnecessary type assertions.
- Prefer `const` over `let` when reassignment is unnecessary.

### Naming examples

```text
ToolCard.astro
BaseLayout.astro
json-formatter.ts
url-encoder.ts
percentage.test.ts
```

### Functions

Functions should have one clear responsibility.

Prefer:

```ts
export function calculatePercentage(value: number, percentage: number): number {
  return (value * percentage) / 100;
}
```

Avoid functions that combine unrelated calculations, DOM manipulation, validation, and presentation.

### Comments

Comments should explain:

- Why a non-obvious decision was made.
- Important limitations.
- Complex algorithms.
- Unexpected browser behavior.
- Important edge cases.

Do not add comments that merely repeat the code.

Write code comments in Russian when a comment is necessary. Keep standard programming terminology and identifiers in English.

Do not translate established technical identifiers merely for localization.

## 9. Validation and Error Handling

Input validation is part of the tool's functionality, not an optional extra.

Every tool should handle invalid and unexpected input safely.

### Validation principles

- Validate input before processing.
- Distinguish empty input from invalid input.
- Handle boundary values.
- Handle unexpected data types where applicable.
- Avoid silently returning misleading results.
- Prevent invalid numeric values from propagating through calculations.
- Provide understandable error messages.

### User-facing error messages

Error messages should be:

- Clear.
- Specific.
- Short.
- Actionable.
- Written for ordinary users, not only developers.

Prefer:

```text
Введите корректное число.
```

Instead of:

```text
Invalid numeric argument.
```

When a technical term is necessary, explain it in accessible language.

For example, a message about absolute zero should help the user understand what the limitation means.

### Contextual explanations

When a tool uses an unfamiliar technical term:

- Consider providing a short explanation.
- Prefer contextual help near the relevant input or message.
- Avoid interrupting the user's workflow.
- Use links to concise explanations when appropriate.
- Keep educational explanations understandable to school students and general users.

Do not add help UI everywhere without a clear need.

## 10. Testing

The project uses Vitest in the Node.js environment.

Tests are located in:

```text
tests/**/*.test.ts
```

### Testing principles

- Add or update tests whenever tool behavior changes.
- Test normal cases.
- Test boundary values.
- Test invalid input.
- Test empty input.
- Test unexpected input where relevant.
- Test regressions when fixing bugs.

### Test quality

Tests should verify observable behavior rather than implementation details.

Prefer focused tests with descriptive names.

Example:

```ts
import { describe, expect, it } from "vitest";

describe("calculatePercentage", () => {
  it("calculates a percentage of a number", () => {
    expect(calculatePercentage(200, 10)).toBe(20);
  });

  it("returns zero for a zero percentage", () => {
    expect(calculatePercentage(200, 0)).toBe(0);
  });
});
```

Do not change or weaken existing tests just to make an implementation pass.

If an existing test reveals an incorrect assumption, investigate the expected behavior before changing the test.

No coverage threshold is currently configured. Do not introduce one without a reason.

## 11. UI and UX Guidelines

The interface should feel consistent across all tools.

### User experience principles

- Make the primary purpose of each page immediately clear.
- Keep the main action easy to find.
- Use clear labels for inputs and buttons.
- Provide useful feedback after actions.
- Make errors understandable.
- Avoid unnecessary visual complexity.
- Avoid excessive animations and decorative elements.
- Keep related controls visually grouped.
- Preserve a predictable interaction pattern across tools.

### Accessibility

- Use semantic HTML.
- Associate inputs with labels.
- Use buttons for actions and links for navigation.
- Ensure keyboard accessibility.
- Provide visible focus states.
- Do not rely on color alone to communicate meaning.
- Use appropriate contrast.
- Give meaningful alternative text to informative images.
- Avoid unnecessary ARIA attributes when native HTML already provides the required semantics.

### Responsive design

All pages and tools should work on:

- Desktop.
- Laptop.
- Tablet.
- Mobile devices.

Do not assume that users have a wide screen or a mouse.

### Design consistency

Before creating a new UI pattern:

1. Inspect existing components and styles.
2. Check whether a similar pattern already exists.
3. Reuse existing patterns where appropriate.
4. Introduce a new pattern only when it provides a clear benefit.

Avoid changing the global visual language for a small local feature.

## 14. Privacy and Security

Privacy is a core product principle.

Tools should process user-provided data locally in the browser whenever possible.

### User data

Do not:

- Send user input to external services without explicit approval.
- Upload user files without explicit approval.
- Store sensitive user input unnecessarily.
- Add analytics that capture user-provided content.
- Log passwords, tokens, or private text.
- Include user data in error reports.
- Persist user input without a clear product requirement.

### Security

- Never commit API keys, tokens, passwords, or credentials.
- Do not expose secrets in client-side code.
- Validate and safely handle user input.
- Avoid unsafe HTML injection.
- Use safe DOM APIs where possible.
- Do not use `eval()` or similar dynamic code execution for processing user input.
- Treat imported files and pasted content as untrusted input.
- Avoid unnecessary third-party scripts.
- Keep dependencies and build tools up to date through deliberate maintenance tasks.

### Password generator

For security-sensitive random values, use the browser's cryptographically secure random number generator where supported.

Do not use `Math.random()` for generating passwords or security tokens.

### Base64 and encoding tools

Encoding is not encryption.

Do not describe Base64 or other simple encoding formats as secure encryption.

## 17. Git Workflow

The project uses Git and GitHub.

### Branches

- `main` is the primary stable branch.
- Create a separate branch for each feature, bug fix, or maintenance task.
- Use descriptive branch names.

Examples:

```text
feat/tool-name
fix/issue-name
content/seo-descriptions
docs/project-guidelines
refactor/shared-logic
```

Do not perform unrelated work on the same feature branch.

### Commits

Use Conventional Commit-style messages.

Examples:

```text
feat: add new calculator
fix: handle empty JSON input
content: improve tool descriptions
docs: update repository guidelines
refactor: simplify validation logic
test: cover temperature conversion edge cases
```

Commits should be focused and describe the actual changes.

### Pull Requests

Prefer Pull Requests when merging changes into `main`.

A PR should include:

- A clear title.
- A summary of changes.
- The reason for the change.
- Relevant validation commands.
- Test results.
- Screenshots for significant visual changes.
- Known limitations, if any.

### Git safety

Do not perform the following actions without explicit user approval:

- Push changes to a remote repository.
- Merge a Pull Request.
- Delete branches.
- Rewrite Git history.
- Force-push.
- Reset or discard user changes.
- Run destructive cleanup commands.
- Overwrite user work.

Before committing:

1. Inspect `git status`.
2. Review the staged diff.
3. Verify that no unrelated files are included.
4. Run relevant checks.

Never commit secrets, generated build output, or local environment files.

Do not assume that a clean local branch means the remote repository is synchronized.

Always verify Git state when it matters.

## 19. Adding New Features

Before implementing a feature:

1. Understand the user problem.
2. Inspect the existing architecture.
3. Check whether similar functionality already exists.
4. Identify the smallest appropriate implementation.
5. Identify the files that need to change.
6. Consider validation and edge cases.
7. Consider accessibility and responsive behavior.
8. Identify the tests needed.

After implementation:

1. Review the code.
2. Run relevant tests.
3. Run `npm run check`.
4. Run `npm run build` when applicable.
5. Review the Git diff.
6. Summarize what changed.
7. Report validation results.
8. Mention remaining limitations.

Do not expand a small feature into a larger redesign unless explicitly requested.

## 20. Bug Fixing

When investigating a bug:

1. Reproduce the problem if possible.
2. Identify the actual cause.
3. Determine whether the issue is isolated or shared.
4. Check whether existing tests cover the behavior.
5. Implement the smallest reliable fix.
6. Add a regression test.
7. Verify that related functionality still works.

Do not hide symptoms with arbitrary conditions or broad exception handling.

Do not silently change expected behavior to make a bug disappear.

Explain the root cause when it is useful to the project.

## 21. Definition of Done

A task is considered complete when applicable conditions are met:

- The requested functionality works.
- Existing behavior has not been unintentionally broken.
- Relevant edge cases are handled.
- Tests have been added or updated.
- `npm run check` passes.
- `npm test` passes.
- `npm run build` succeeds.
- The interface is usable on relevant screen sizes.
- No unrelated changes were introduced.
- The Git diff has been reviewed.
- Documentation or backlog has been updated when necessary.

If some conditions do not apply, explain why.

A successful code edit alone does not mean the task is complete.

## 22. Final Response Format

After completing a task, provide a concise report.

Use this structure:

### What changed

- Describe the implemented changes.
- List important files affected.

### Verification

- List commands executed.
- Report actual results.
- Mention checks that were not run.

### Important notes

- Mention limitations, assumptions, or remaining work.
- Identify any decisions that require user approval.

Do not claim success without verification.

Do not hide failed tests or warnings.

Keep the report concise, factual, and useful.

Build Utilix as a reliable collection of small, useful tools.
